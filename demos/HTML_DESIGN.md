# 教学用 HTML 设计原则

适用范围：给《编译原理》这类"机械步骤"型算法做可交互演示（LR 分析、算符优先、DFA 构造、递归下降……）。

参考实现：`demos/lr-parse-animation.html`（约 380 行，单文件，零依赖）。
本文的每一条都是从那份实现的返工过程里抠出来的，不是先验的美学主张。

---

## 零、先判断该不该做 HTML

Typst 笔记负责"完整可查"，HTML 负责"当场看懂"。两者不重叠。

值得做成 HTML 的，是那些**用一个静态表格讲不清、必须看它怎么动**的东西：

- 栈、指针、状态在每一步怎么变；
- 表的某一行一列"为什么这次查这里"；
- 一个动作（归约）内部还藏着几步。

不值得做的：定义、分类、对比、流程框图。这些用 `#definition` / `#table` 写在笔记里就好。
把定义搬进 HTML 只会得到一份更难读的笔记。

---

## 一、屏幕是讲台，不是资料库

这是唯一的总原则，下面所有条目都是它的推论。

一次投屏、一个学生、一块屏幕。屏幕上每多一样东西，注意力就被摊薄一次。
判断标准很简单：**删掉它，学生会不会看不懂？** 不会就删。

第一版实现里堆了图例、进度条、完整过程表、键盘提示、产生式面板、答疑卡片、播放按钮、速度选择、多输入串预设、句型条——
用户的原话是「完全在喧宾夺主」。
最后留下的只有三样：**文法、两个栈、分析表**，加一句动作说明。

### 删掉的清单（都是实际写出来又被砍掉的）

| 元素 | 为什么该删 |
| --- | --- |
| GOTO 空白答疑卡片 | 概念解释属于笔记正文，不属于演示界面；它在抢表的位置 |
| 键盘快捷键 + 提示行 | 演示者用鼠标点，不需要第二条操作路径 |
| 自动播放 + 速度选择 | 见第三节：自动播放与"一步一变"直接冲突 |
| 完整过程表（51 行） | 那是笔记里的表；在 HTML 里它只是同屏的第四份信息 |
| 图例（颜色→含义） | 颜色若语义正确，看一眼就懂；需要图例说明配色就是配色失败 |
| 句型条（栈内符号 + 剩余输入） | 与"两个栈 + 输入串"重复，等于把同一件事画了两遍 |
| 进度条 / 进度数字 | 保留 `12 / 51` 这种极小计数即可，不必再画一根条 |
| 多输入串预设按钮 | 一堂课讲一个串。多串是笔记的事，是演示的分支成本 |

> 如果某个元素是"为了完整性"而存在，它就该出现在笔记里，不该出现在演示里。

## 二、三样东西，一个都不许省

演示界面必须同时可见、且位置固定：

1. **文法** —— 顶端一行。学生每次看到 `r6` 都要回头找第 6 条产生式，找不到就断了。
2. **两个栈** —— 主体。竖向成对显示（状态 / 符号），横向排列。
3. **分析表** —— 底部整行。它是"答案册"，栈是"演算纸"，两者必须同屏对照。

三者的相对位置就是阅读顺序：读文法 → 看栈 → 查表。
任何打断这条链的布局（表在侧栏、栈在卡片里、文法折在说明里）都要改。

## 三、一次点击 = 一次状态变化

这是用户提得最狠的一条：**不要把归约的连续好多步变化塞在一个下一步中**。

算法手册里"归约"是一个动作，但在学生眼里它是四件事：

| 点击 | 屏幕变化 | 表上的高亮 |
| --- | --- | --- |
| 查 ACTION | 无 | ACTION 行×列交叉格 |
| 移进 | 栈尾 +1 符号 +1 状态，指针右移 | 无（上一格已完成） |
| 归约 ① 找句柄 | 栈顶 m 组标红划掉，栈不动 | 无 |
| 归约 ② 弹出 | 才真的弹出 | 无 |
| 查 GOTO | 无 | GOTO 行×列交叉格 |
| 归约 ③ 压回 | 才压入左部 + 新状态 | 无 |

`i+i*i` 因此从"14 行表格"变成 **51 步**。数字变大不是缺点——每一步都能停下来讲。

拆分的判据：

- **一次点击只允许一个栈操作**（压入 xor 弹出 xor 不动）。
- **"查表"和"用表的结果改栈"必须是两次点击**。查表那一下只高亮，栈不许动。
- **"要弹出哪些"和"弹出"必须是两次点击**。先标红让学生确认是这几组，再弹。
- 说不清这步改了什么，就是这步拆得不够。

### 由此直接排除自动播放

自动播放把"点击"变成"等待"，学生失去停下来的权力，而且天然会把多步压成一段动画。
默认节奏是 800ms/步时，51 步里没有任何一步来得及看清。
**不做自动播放，不做定时器推进，不做"一次播完"按钮。** 只有 上一步 / 下一步 / 重置。

## 四、版式：表在下，栈横排，字要大

### 栈横排

竖向栈（栈顶在上）是教材画法，但在屏幕上它会和输入串、说明挤在同一列，视线来回跳。

横向更符合"读"的习惯：

- **左边栈底，右边栈顶**，栈顶那一列加浅底 + 实心圆圈，一眼定位。
- 状态和符号**分两行、同一列对齐**。这样"第 i 个状态配第 i 个符号"是视觉事实，不用数。
- 栈底占位用一个空符号列，保证状态行和符号行永远等长。

### 字要大

演示是投影，不是阅读。字号从小往大调，直到"最后一排能看清"：

| 元素 | 参考字号 |
| --- | --- |
| 输入串 | 30px，等宽 |
| 栈里的符号 | 30px，等宽，加粗 |
| 栈里的状态 | 17px |
| 表内单元格 | 17px |
| 当前动作公式 | 21px，等宽 |
| 说明文字 | 15px |
| 小标签（状态/符号、提示） | 12.5–13px |

17px 是这张表的下限；栈里的符号必须比状态大，因为符号才是语法对象。

### 表在下

表占满整行放在最底部，而不是塞进右侧栏。
理由：右侧栏会让表被压窄、字号被迫缩小，而"行×列交叉格"是这张表唯一要传达的信息，压缩它等于毁掉它。
整行宽度还让 12 行 × 10 列能一次看全，不用滚动。

## 五、色彩：一种动作一种色，且只用于语义

配色不是装饰，是教学信息。固定一套，不随手加色：

| 语义 | 色 | 用在 |
| --- | --- | --- |
| 移进 shift | 绿 `#0d8a68` | 表里的 `S₅` |
| 归约 reduce | 红 `#c53f3f` | 表里的 `r₆`；被弹出/划掉的栈元素 |
| GOTO | 紫 `#7a4bc4` | 表里的 GOTO 数字、GOTO 公式、压回时的左部 |
| 当前动作 | 蓝 `#2f5fd0` | 栈里的符号、当前 ACTION 格高亮、栈顶圈 |
| 中性 | 灰阶 | 其它一切 |

规矩：

- **红只表示"要消失"或"错误"**。红色出现在划掉的句柄上，学生立刻懂"这段要没了"。
- **紫色只表示 GOTO**。紫色数字出现在表里，就一定是在说"这个状态是从 GOTO 来的"。
- **高亮要同时标行头和列头**。只亮格子，学生还得自己找是哪一行哪一列。
- **同时只允许一组高亮**。切步时先清空全部，再上新的；两处蓝框等于没有蓝框。

## 六、文案：一行公式 + 一句话

说明区永远只有三部分，从上到下：

```
归约 r3 · ① 找句柄          ← 12.5px 灰，说明"这是哪一步"
T → T * F，右部 3 个符号     ← 21px 等宽，公式/结论
r3 要求把栈顶这 3 组（红色划掉的部分）换成一个 T。   ← 15px，一句人话
```

- 标签里的序号（①②③）和表里的 `r3` 必须同名，学生才能对上。
- 那一句话**只讲此刻屏幕上看得见的东西**，不讲下一 步、不讲原理、不讲"为什么设计成这样"。
- 句子用加粗标出**唯一需要盯住的那个对象**（`3 组`、`F`、`acc`），不要整句加粗。
- 不写段落。超过两行就说明这一步还没拆干净。

## 七、工程前提：先算轨迹，再渲染

"一步一变"不是靠动画调参实现的，是靠**把过程预先摊平成数组**。

```js
// 1) 先算：整条轨迹拍成一维 steps，每项是一帧完整快照
const steps = [];                       // 每项 = { stack, ptr, hl, mark, fresh, kind, formula, say }
while (...) {
  steps.push({ stack: snap(stack), ptr, hl: {...}, kind: '查 ACTION 表', ... });  // 查表：栈不动
  if (shift) steps.push({ stack: snap(newStack), ptr: newPtr, fresh: true, ... });
  if (reduce) {
    steps.push({ ..., mark: m });        // ① 找句柄，栈不动
    steps.push({ ..., stack: popped });  // ② 弹出
    steps.push({ ..., hl: {goto} });     // ③ 查 GOTO，栈不动
    steps.push({ ..., stack: pushed });  // ④ 压回
  }
}

// 2) 再渲染：一帧对应一次点击，render() 只认 idx
let idx = 0;
function render() { /* 用 steps[idx] 画栈、画输入串、标高亮、写文案 */ }
$('#btnNext').onclick = () => { idx++; render(); };
```

这样做的好处：

- 每个"下一步"都是**幂等、可回退**的，上一步不需要反算；
- 拆步的粒度由 `steps.push` 的次数决定，改粒度不改渲染代码；
- 没有异步、没有定时器、没有竞态，一个文件、一个 `idx` 就是全部状态；
- 跳转某一步 = 改 `idx`，所以 `#s=41` 这种锚点能直接用来备课和截图。

反面做法：用 `setTimeout` 串起一段动画再让用户点"下一步"——这就回到了第三节禁止的那种东西。

## 八、验收清单

投屏前逐条打勾。任一条不满足就回去改。

- [ ] 屏幕上只有三块：文法、两个栈、分析表。
- [ ] 文法在顶端始终可见，产生式带编号。
- [ ] 栈横排，左栈底右栈顶，状态与符号上下对齐。
- [ ] 表在底部、占满行宽、12 行能一次看完不滚动。
- [ ] 栈里符号 ≥ 24px，表内 ≥ 16px。
- [ ] 没有任何自动播放、定时器、速度控件。
- [ ] 每次点击只改一处：压入 / 弹出 / 只高亮。
- [ ] "查表"和"改栈"在两次不同的点击里。
- [ ] 同时最多一组高亮，且行列头同时亮。
- [ ] 红色只出现在"要消失的东西"和"错误"上。
- [ ] 说明区 = 小标签 + 公式 + 一句话，不超过两行。
- [ ] 删掉任意元素都答不出"会不会看不懂 → 不会"，则继续删。

## 附：常见返工模式

我在这份实现上被连续打回三轮，模式很固定，可以直接避开：

| 症状 | 病因 | 处方 |
| --- | --- | --- |
| 「太花哨」 | 把"能想到的信息"都放上屏 | 先做减法到只剩三块，再加东西要有理由 |
| 「喧宾夺主」 | 辅助说明比主体更显眼 | 任何卡片/面板的面积与字号都不许超过栈和表 |
| 「不要塞在一个下一步里」 | 复刻了算法手册的动作粒度 | 按"学生要看见的变化"拆，不按"算法的定义"拆 |
| 「横着排、字大点、表放下面」 | 沿用了教材竖版画法 | 屏幕版式服从投影与阅读，不服从纸面习惯 |
